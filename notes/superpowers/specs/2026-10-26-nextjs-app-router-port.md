# Next.js App Router port

Requested by Donald on 2026-10-26 ("improve quesar.cloud website with modern next js and new styles"). Asked about `AGENTS.md`'s rule that this repo superseded the Next 16 `MLAI-CORPORATION-WWW` site and must not revive it, Donald chose to port to Next.js anyway. That retired checkout stays retired: this is a port of _this_ repository's source, not a revival of the old one. The "new styles" are the blueprint instrument redesign (`2026-10-25-blueprint-redesign.md`), finished and verified on `design/blueprint-instrument` first. The port branch `next/app-router-port` builds on it.

`AGENTS.md` and `CLAUDE.md` still describe TanStack Start as the framework. Update them in the change that makes Next.js the production build (stage 3), not before.

## Approach: strangler, not rewrite

The site is 74 TanStack file routes and about 64k lines of TypeScript, with Better Auth, server functions, PGLite, a static publish pipeline and a 226-case Playwright suite. A rewrite would freeze the site for weeks and lose that suite as a safety net. Instead, both builds run from one source tree:

- `app/` is the Next.js App Router tree. `scripts/next-routes.ts` generates one `page.tsx` (server: params, `generateStaticParams`) and one `view.tsx` (client: mounts the route) for each TanStack route, keyed by its `createFileRoute("…")` id. `--check` fails on drift, as `routeTree.gen.ts` would. Hand-written: `layout.tsx` (ported `__root.tsx`), `not-found.tsx`, and three force-static route handlers (`/feed.xml`, `/search-catalog.json`, `/github-snapshot.json`).
- `src/compat/next/` maps the TanStack surface this repo uses onto Next: `Link`, `useNavigate`, `useRouter`, `useRouterState`, `useHydrated`, `Navigate`, `notFound`, `redirect`, `Route.useParams/useSearch/useLoaderData`, `getRouteApi`, plus TanStack's search serialisation. `RouteView` runs the route's loader, merges its `head()` over the root defaults with TanStack's dedupe rule, and renders the tags, which React 19 hoists into `<head>`. `ssr: false` routes render after hydration.
- `next.config.ts` aliases `@tanstack/react-router` and `@tanstack/react-start` to the compat layer for webpack. Type checking still uses the real TanStack types (`tsconfig.next.json` includes `src/`, so `routeTree.gen.ts` registers the routes).

## Stages

1. **Static parity (done, `next/app-router-port`).** `output: "export"`, webpack. URLs keep the live shape (`/docs`, no trailing slash); `scripts/next-export.ts` moves each `docs.html` to `docs/index.html` for GitHub Pages. Links preload on intent (hover/focus), as TanStack's `defaultPreload: "intent"` did, not on entering the viewport. The build is static-mode only (`VITE_STATIC_SITE=true`, auth off), which is what quesar.cloud serves today. Server-only modules (`*.server.ts`, `@/lib/db`, `@/lib/server/*`) are swapped for a throwing stub, and `createServerFn` returns a rejecting function, because the static build renders `ServerOnlyNotice` before any of them could run. Deferred: `/quasar/site/$id` (ids exist only at runtime). The GitHub build snapshot is a force-static route handler, `/github-snapshot.json`.
2. **Server runtime (done on `task/next-stage2-server`).** `QUESAR_NEXT_MODE=server` (`bun run next:build:server`, `next:dev:server`, `next:start`, port 3101) builds the full site, not an export:
   - **Server functions** keep their source. A webpack pre-loader (`scripts/next-transform.ts`, unit-tested) does what the TanStack Start compiler does: in browser bundles each `createServerFn(…).handler(fn)` becomes `.handler("<module>#<n>")`, so handler bodies and their server-only imports never ship; on the server the id is appended and `.handler(fn, id)` registers the function (`src/compat/next/start-server.ts`). The browser stub (`start-client.ts`) POSTs to one dispatcher, `app/api/server-fn/[id]/route.server.ts`, which applies TanStack's default CSRF rule (`csrf.ts`, vendored and tested), runs middleware → validator → handler inside an `AsyncLocalStorage` request scope (`getRequest`, `setResponseHeader`), and replies in seroval JSON, TanStack's own serializer. `UnauthorizedError` maps to 401. Every call is a POST, so every call is CSRF-checked; the `method: "GET"` hint is not used for caching.
   - **Server routes** (`src/routes/api/*`) become generated `route.server.ts` handlers calling the same `server.handlers` (`api-route.ts`); a `$` splat arrives as `_splat`, as on TanStack.
   - **Request middleware** from `src/start.ts` is `proxy.server.ts` (Next 16's `proxy`): readiness (`/api/readiness`, refusal until the deployment is configured) and the report-only CSP headers on pages.
   - **`import.meta.glob`** (migrations, telemetry route keys) is expanded at build time by the same loader; `?raw` files load as source.
   - **Server-only files** use `.server.ts(x)`, an extension only server mode adds to `pageExtensions`, so the static export never sees them. `/quasar/site/$id` is a `page.server.tsx`, rendered per request.
   - **Async loaders** (`/login`'s sign-in methods) suspend through `use()` on a cached promise. Pages without dynamic APIs are still prerendered at build, so `/login` lists the sign-in methods configured in the build environment; Vercel builds with the runtime environment, so they match there.
   - Verified on localhost: Better Auth email sign-up through the UI, session, `authMiddleware` functions (signed in and refused signed out), CSRF refusal, validator errors, inquiries written to PGLite, telemetry, CSP report, cron refusal, workspace routes, every page class, and the console rendering for a signed-in user with no browser console errors. Not verified: OAuth providers, passkeys, Stripe, Turnstile, LLM providers and a real Postgres `DATABASE_URL`, which need credentials this machine does not have.
3. **Cut-over (done on `task/next-stage2-server`).** Next.js is the only build:
   - Vite, Nitro, `@tanstack/react-router` and `@tanstack/react-start` are removed (`vite.config.ts`, `routeTree.gen.ts`, `__root.tsx`, `src/start.ts`, the virtual-module, search-retry and prerender plugins, `copy-pglite-assets`). The film capture pipeline (`e2e/film`) runs `next dev` in static mode instead of a Vite config.
   - The compat layer became the site's own framework module, `src/framework/`. Every import moved to `@/framework/router` and `@/framework/server-fn` (test mocks too). It is typed, not a shim: path params come from the route string, loader data and search from `loader` and `validateSearch`, server-function `data` and middleware `context` are inferred, zod schemas are accepted as validators (Standard Schema), and a generated `route-registry.gen.ts` types `getRouteApi`, as `routeTree.gen.ts` did. `src/` typechecks with no TanStack package installed.
   - Scripts: `dev` (Next server mode, 8080), `build` / `build:persistent` (server), `build:static` (export, `next-export`, `publish-static` from `out/`), `start`/`preview` (8081), `routes`, `check:parity`. `vercel.json` sets `framework: nextjs` and carries the audit-expiry cron; PGLite's wasm and data are traced into the deployment; the persistent-mode guard runs in `next.config.ts`; Better Auth uses `nextCookies()`. The Next build id is the source commit, so rebuilding unchanged source reproduces `docs/`.
   - `check-static` reads Next's output: initial scripts are `<script src>` (skipping `nomodule` legacy polyfills) plus script preloads; budgets are unchanged and every route fits. `check-static` counts only scripts the HTML names, which undercounted the Vite build: it fetched part of each page's code in a second hop (for example `/docs` loaded the research dataset only once `docs-hub` asked for it), while Next lists every chunk up front. Measured in a browser as every script a page loads until network idle (gzip, 2026-10-26), the Next export is 6–8% heavier with a third fewer requests: `/` 225.5 KB / 21 scripts vs 210.6 KB / 32, `/docs` 266.8 KB / 25 vs 250.8 KB / 39, `/research` 253.8 KB / 24 vs 237.5 KB / 37, `/developers` 242.9 KB / 26 vs 225.4 KB / 42. The ~15–17 KB difference is the framework runtime (Next's client runtime and React DOM against TanStack's), not app code.
   - The export has 12 pages the published site lacks: `/source/*` pages that `repoPaths` (src/lib/catalog.ts) declares canonical and the GitHub panels link to at runtime, which the Vite crawl never reached, so those links 404 on the live site today. The sitemap grows from 118 to 130 entries accordingly.
   - `publish-static` was run for real on the export (then `docs/` restored): `.nojekyll`, `CNAME`, robots and sitemap correct, no 404 in the sitemap, `check:static` passing on the result. Its asset check reads only `src`/`href` attributes, decoded (a test covers the Next markup).
   - Fixed on the way: the 404 page no longer declares a canonical URL; SVG imports (Next yields `{ src }`) go through `src/cinematic/design/mark.ts`; `next dev` is kept out of `AGENTS.md` (`agentRules: false`).
   - Backend acceptance harnesses (`e2e/backend/*`, opt-in with `QUESAR_BACKEND_ACCEPTANCE=1` and a passwordless disposable Postgres on 127.0.0.1:55471) are ported. They used to start `vite dev` (or Nitro's `.output/server/index.mjs`) and import source modules into the page to call server functions. Now:
     - The durable, AI-consent and commerce suites start `e2e/backend/next-dev-server.ts`: the server build in dev mode (`next({ dev: true, webpack: true })`) in one process, with its own `.next-acceptance` dist dir. They don't use the `next dev` CLI because it forks its server into a child that survives a SIGKILL of the CLI and keeps the port. The harness signals only processes it owns, and the durable suite kills its app with SIGKILL on purpose.
     - The persistent suite serves the `bun run build:persistent` output (`.next-server`) with `next start` behind its TLS proxy. Its artifact hash skips the `cache/` and `trace` entries that `next start` writes at runtime. It refuses to run while any `.env*` file is present, because `next start` would load it.
     - Server functions are called from the page through the dispatcher, a same-origin `POST /api/server-fn/<id>` (`e2e/backend/server-fn.ts`). Ids come from running `scripts/next-transform.ts` over the source module, so they match what the build registers. `askPersonaFromClient` is called as `askPersona`, the server function it wraps outside the static site. The AI-consent policy-failure fixture fails only the `getConsoleStatus` call, because every server function is now a POST.
     - Two Next differences surfaced as test fixes. First, Next renders a `role="alert"` route announcer, so alert assertions now filter by their text. Second, the durable suite waits out a fixed 10-minute rate-limit window boundary that a run once straddled (03:40:00); the limiter itself still refused the sixth inquiry when reproduced directly. The durable and AI-consent timeouts are now 600 s because dev compiles are slower.
     - Run on 2026-10-26 against a passwordless Postgres 17.11 cluster on 127.0.0.1:55471, Chromium only:
       - durable: passed, 1.6 min.
       - AI-consent: passed, 1.6 min. It used the synthetic provider fixture only, so live-provider acceptance is still blocked.
       - persistent: passed, 12.7 s, against a `build:persistent` artifact. The artifact hash was unchanged.
       - commerce: passed, 7 tests in 1.2 min, against the Rust `wdbx` binary (release build of WDBX `4c01514`, SHA-256 `0496084c44cde6bdcf5a7c45e5d9ace2f3df39a90f4d8d01f96d365fb4a853ff`, passed as `QUESAR_ACCEPTANCE_WDBX_BINARY`); `assertHarnessPorted()` is gone. The Zig `wdbx typed` executable used on 2026-10-09 (at `/Users/donaldfilimon/dev/active/wdbx/zig-out/bin/wdbx`, under four different SHA-256s that day) no longer exists anywhere reachable and its source was never in the WDBX repository, so WDBX `4c01514` reimplemented the same CLI contract over V2Store; this run is a new Rust witness, not continuity with the Zig runs. The tests that read the Zig `zig-v4.wal` now scan the invoice's v2 `journals/` files for the same plaintext absence. `src/lib/server/commerce.server.test.ts` passes (8 tests) with `WDBX_TEST_BINARY` set to that binary; it has no default path any more, so `bun run test` fails without it rather than reading a machine-specific path.
     - `bun run typecheck` also fails in `tsconfig.migration.json`, on frozen evidence under `notes/verification/` that imports absolute `/Users/donaldfilimon/...` paths. This is unrelated to the harnesses.
   - Server mode is the default and the export opts in (`QUESAR_NEXT_MODE=static`): Vercel's Next builder reloads `next.config.ts` without the build script's environment, and must see the same `distDir` and output mode the build used.
   - Vercel removed (2026-10-26, Donald's request): `vercel.json` is gone, so nothing schedules the audit-expiry cron and the server build has no host; GitHub Pages (the static export) is the only deployment. The Vercel preview deployment had been failing on every commit, including before the port.

## Acceptance for stage 1

- `bun run next:build` generates and statically exports every route except the deferred one.
- `bun run next:check`: every page in `docs/` exists in `out/` with an identical `<title>`, description and canonical URL, and every exported page renders the site shell.
- The Playwright suite passes against `out/` (`E2E_STATIC_ROOT=out bunx playwright test`) and still against `docs/`. Three test changes are build-agnostic: asset matchers accept both builds' file names (`search-panel-<hash>` and `search-panel.<hash>.js`), and alert assertions are scoped to `<main>`, because Next adds a page-level `role="alert"` route announcer.
- `bun run typecheck` (now including `tsconfig.next.json`) and `bun run lint` pass. The Vite build and its gate are unchanged.

## Not covered by stage 1

Server features (sign-in, console, admin, Quasar, inquiries, billing) behave as they do on the static site today: a notice, no network. JS budgets in `scripts/check-static.ts` measure Vite chunks and have no Next equivalent yet. Stage 3 sets them.
