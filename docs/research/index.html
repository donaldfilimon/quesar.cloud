Topics

Precise language. No borrowed benchmarks.

If a number is not produced by a repository test or a documented artifact, it does not appear here.

Memory architecture

●Current

Episodic records with WAL, MVCC, causal DAGs, and content addressing. Memory is a substrate, not a chat log with embeddings glued on. Applies to WDBX, ABI.

Retrieval

◐Partial

Ordered vector search and hybrid ranking contracts exist. Collapsing semantic, temporal, causal, and persona signals into one score is a documented limitation. Applies to WDBX.

Distributed systems

◌Experimental

Reference cluster replication and read repair are in source. They do not establish production sharding or hosted authority. Applies to WDBX.

Model orchestration

◐Partial

Scheduler, plugins, MCP, exact model registry. Routing is explicit. Quality is not inferred from a successful template completion. Applies to ABI.

Privacy and local inference

●Current

Default posture is operator-owned machines. Remote is optional. This website does not see your documents, weights, or generated output. Applies to Quesar, Abbey, ABI.

Provenance and trust

◐Partial

Signatures and causal history answer why a record is trusted. They do not make the record true. Federation evidence is separately authorized. Applies to WDBX, Abbey.

Synchronization

○Planned

Mobile CloudKit and encrypted-local fallback are distinct. Signed-device acceptance is not the same as a web export. Applies to Quesar, mobile.

Interoperability

◆Research

Workspaces, crates, and apps share a type vocabulary for product, persona, and claim provenance. Semantic UI tokens remain app-local. Applies to Quesar.

Implementations

Nested cases. Each one names the source it depends on.

These sit under /research/implementations. They are implementation readings, not extra benchmark claims.

ai · wdbx · sea · gpu · mcp · tui

A six-layer architecture for evidence-aware AI systems

Quesar organizes interface, orchestration, retrieval, acceleration, storage, and audit as distinct layers so that evidence and runtime claims can be traced to the component that actually supports them.

ai · wdbx

A private document pipeline with explicit fallback behavior

The private Quesar application implements bounded ingestion, workspace-scoped extraction and search, and consent-gated model access while making degraded retrieval behavior visible instead of silently changing providers.

ai · wdbx

Mobile Vault persistence across CloudKit and local fallback

The Quesar mobile Vault keeps one CRUD contract while selecting either the user's private CloudKit database or an encrypted local SecureStore fallback and exposing the selected backend to the application.

ai · mcp · tui

Quasar as a bounded repository-generation loop

Quasar couples an Anthropic tool loop to a narrowly constrained project filesystem, producing a local application through inspectable read, list, and write operations rather than granting an unconstrained shell.

ai · wdbx · sea · gpu · mcp · tui

Abbey capability claims as an executable ledger

Abbey centralizes capability statements in a typed registry whose status, evidence, dependencies, feature flags, and refusal behavior can be projected into documentation and checked for drift.

ai · wdbx · sea · gpu · mcp · tui

WDBX Specimen separates architecture, runtime profiles, and proof

WDBX Specimen combines a provenance-aware architecture specification with explicit browser and native runtime profiles, then uses conformance tests to make a bounded subset of the design executable.

ai · wdbx

Deterministic research exports with citation gates

The Quesar research export pipeline converts validated publication records into stable JSON and static HTML, verifies and copies declared attachments, and records content digests while enforcing unique identifiers, public source URLs, and canonical links.
