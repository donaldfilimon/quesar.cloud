Quesar

Infrastructure for private, persistent, adaptive AI.

Quesar is the product experience that connects ABI, WDBX, and Abbey. It is not a chatbot, not a vector database, and not a hosted wrapper around a public model.

◐PartialPublic orientation and a signed-in console are current. Hosted assistant sessions are not.

What it is

A system you can place, inspect, and bound.

Quesar exists because intelligence that forgets you at the end of every session is not a foundation you can build on — and intelligence that requires you to surrender memory to a remote cluster is not a foundation you should have to accept.

Who it is for

Developers, technical organizations, and privacy-conscious operators who need AI systems that keep context, expose provenance, and run across local, edge, and optional remote compute.

How it differs

Conventional apps bolt memory onto a chat transcript. Quesar treats memory as a substrate (WDBX), orchestration as a runtime (ABI), and the assistant as an experience (Abbey) — with claim-honest status on every surface.

What you can build

Local assistant workflows with inspectable context. Retrieval over signed episodic records. Tools and plugins under ABI contracts. A local site-generation loop that writes a real Next.js project onto disk.

What you cannot assume

This website does not provision an assistant or generate sites. Sign-in opens a console for field notes, not an Abbey session. The local builder does not host, deploy, or bill. Production sharding is not established.

Name

Quesar is the product. Quasar is the local builder.

They are not interchangeable. This repository keeps the builder service at sidecars/quasar-service and its screens at /quasar/sites; the website is this app.

Quesar

The infrastructure product: orchestration, private memory, local compute. This site is orientation for that product.

Quasar

A local v1 website builder: generate a Next.js project and preview it on your own machine. Bun 1.4, Anthropic credentials, a service and Expo app. Hosting, deploy adapters, and builder authentication are outside this version.

Quasar v1

Four parts. Preview means next dev on your machine.

From the integration README. Unit suite is not a live Anthropic generation.

  1. 01

    packages/shared

    TypeScript types and zod schemas shared by the service and the Expo app — Site, GenerationEvent, PreviewStatus, request bodies.

  2. 02

    sidecars/quasar-service

    Local Bun service (default port 4700): registry, path guard, site filesystem tools, generation engine, scaffolder, preview manager.

  3. 03

    templates/next-site

    A buildable, checked-in Next.js 16 + Tailwind v4 starter, copied per-site as the generation baseline. Own lockfile, outside the root workspace.

  4. 04

    /quasar screens

    Sites, new site, site detail with live events and preview, and settings, in this app. They call the local service from your browser. There is no deploy step in v1.
